# 分析超时：2026-10-07 修复与验证

## 已定位的程序问题

旧 `requestModelChat` 给每个尝试套完整 30 秒截止时间。这个计时器覆盖连接及整段流式正文，即使模型已经开始持续返回工具参数，也会在 30 秒中止、重试；60 秒总时限可能再次截断后续尝试。

旧本地计时器与真实上游 HTTP 504 共用 `model_gateway_timeout`。用户记录中的「首次建议 23 秒、规划 60 秒、重试一次」不能单独证明上游是否返回过 504；现在逐次记录来源，避免把本地中止说成模型断连。

## 当前行为

- 首次有效输出等待默认 **30 秒**，包括连接及响应头等待。响应头、SSE 心跳、空增量、usage 和内部推理不延长这个等待。
- 开始返回公开内容或工具参数后，改为默认 **15 秒连续停滞检测**。持续有效输出不因累计超过 30 秒而重新提交。
- 整个后端规划（模型请求、查证、修复及退避）仍有 **60 秒总上限**；前端保留自己的全流程、截图和执行校验截止时间。
- 仅首次输出等待 / 输出停滞等可恢复错误允许在剩余总预算内重试，分析最多两次；鉴权、参数、额度错误不重试。硬总时限和用户取消不会启动新尝试。
- 所有规划请求向上游请求流式输出，JSON 客户端仍收到普通 JSON。上游退回非流式 JSON 时，其完整正文受首次输出等待约束，不能仅凭响应头无限等待。
- 不改变 Max 分流、方案工具、输出长度、执行校验、确认和撤销。图片请求的重试、去重及不明任务状态保护不变。

## 配置

`MARKSET_MODEL_TIMEOUT_MS` 保留兼容，但含义是首次有效输出等待，不再是整段流式输出时限。

`MARKSET_MODEL_IDLE_TIMEOUT_MS` 为有效输出之间最大空闲时间（默认 15000，限制 5000–30000）。`MARKSET_MODEL_TOTAL_TIMEOUT_MS` 仍不超过 60000。

`/api/health` 的分析策略增加 `firstOutputTimeoutMs`、`idleTimeoutMs`；`attemptTimeoutMs` 是兼容别名。

## 诊断与隐私

不同错误分别为：

| 诊断码 | 含义 |
| --- | --- |
| `model_first_output_timeout` | 本地连接或首次有效输出等待超时；阶段细分为 connect / first-output |
| `model_stream_idle_timeout` | 本地连续有效输出停滞 |
| `model_total_timeout` | 后端规划总预算耗尽 |
| `model_gateway_timeout` + upstream / provider | 上游真实返回 HTTP 504 |

Agent 记录展示每个逻辑调用 / 尝试的 HTTP 状态、响应头时间、首次和末次有效输出时间、耗时及中止来源。HTTP 200 的本地中止不会显示成上游 504。首次有效输出与首次公开建议草案是两个独立指标。

最多保留 12 条白名单化尝试元数据，不记录密钥、提示词、完整页面、原始输出或内部推理；这些记录只供展示，不发送为额外模型历史。失败后仍保留笔迹、输入，且不应用兜底方案。

## 验证及边界

- 400 项自动测试通过；`npm.cmd run build` 通过。
- 使用可控时钟模拟实际 30 / 15 / 60 秒策略：首次输出 23 秒、完整计划 35 秒只需一次请求；纯心跳不能续命；停滞会取消正文读取；持续输出仍在总时限结束；父级取消与安全重试缓冲隔离正确。
- 真实 `brushIntent` Max 路径（假上游）验证慢方案完整形成、仍需用户确认，并记录安全元数据。
- 本地 HTTP 端点、前端 API、真实控制器和记录面板验证来源传递、失败后的输入 / 笔迹保留，以及图片可靠性回归。
- 独立 Chrome 的 11 项界面断言通过：圈选、输入、超时、手动重试、两种来源的记录显示；模拟两个分析响应，未调用付费分析或生图服务。
- 当前 localhost:5173 的健康检查已反映新策略；未接管或终止用户的终端进程。

这次验证消除了程序误截断健康流的可复现问题，不等于已经证明真实百炼延迟或 504 故障消失。上游排队、长方案超过总时限等仍可能发生，后续可以依据新的逐次时序判断具体瓶颈，而不是盲目增加重试或降低模型质量。
